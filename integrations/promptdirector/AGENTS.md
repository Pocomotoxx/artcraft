# PromptDirector Development Entry

PromptDirector is a local-first library of visual creative inspiration, serving users in saving, organizing and reusing visual cases and complete creative material. This repository maintains the product source code, tests and public release material; for everyday local testing, load `extension/`.

## Getting Started and Resuming

At the start of every new conversation and after context compaction recovery, this file must be read, and, according to the current task, the [development notes](docs/DEVELOPMENT.md), the relevant source code and tests must be read.

Rely on the current request, the README, the relevant source code and tests; content that has not been read or verified cannot be treated as fact.

## Development and Delivery

- Before modifying, check the live Git state and protect existing changes; follow the complete user task to trace shared rules and consumers.
- Complete material first: keep originals, full text, original prompts, sources and their correspondences; previews, summaries and AI inferences must not pose as original material. Sources are protected by default, and explicit corrections are handled separately; creative content may be edited precisely.
- Design by the complete task: follow the stages of finding, reading, selecting, editing and organizing, storing back and read-back checking; the interface, the internal composer and external Agents share fields and business rules.
- Manual context first: use explicitly chosen material accurately, recommendations do not override selections, old commands do not overwrite new edits, and references in execution do not change as browsing continues; one selection does not automatically become a long-term preference.
- Concise yet complete: common actions are completed in place and low-frequency recovery is placed back in the corresponding operation step; an undo that affects data must state the object, scope and impact on later edits and be confirmed before execution. Merge duplicate entries, reduce detours and unnecessary confirmations; do not bind independent tasks together, and do not trade away effective capabilities or pile up explanatory copy for the sake of conciseness.
- Consistent experience: before modifying the UI, you must read the applicable visual guidelines, look at the target live page and shared components, and state the rules followed this time and the shortest operation path; do not ask again for confirmation that exists. Before delivery, you must actually view the final wide and narrow screenshots and the relevant empty/waiting/failure states, checking redundant copy, ineffective actions, contrast, occlusion, jumping and focus; passing tests or having no overflow alone must not be called visual acceptance passed, and not having viewed the real screen must be clearly marked as unverified.
- Interface subtraction is an acceptance condition: every permanent piece of copy must help the user judge or act; delete development comments, implementation notes, duplicate titles and duplicate counts, and do not use explanations to make up for vague operations. Buttons express only actions, and the title, back and operations of the same group share one row and are aligned when space allows; color tags are not made into eye-catching primary buttons. Enter, exit, back and close work consistently by the current level, and only controls valid in the current mode are shown. Content that can be judged reliably automatically is not made to be filled in again by the user; only matters involving cost, irreversible consequences or real capability limits are handed explicitly to the user to decide. Before slimming down an entry, confirm that the complete capability is covered by the retained entry.
- Work can continue: keep applicable selections, playback positions, drafts and layout; distinguish closing a view, cancelling a task and deleting results. Long tasks have real progress, successful parts are kept, and failed parts can be skipped or retried. Errors are shown in place without blocking, and a failure of auxiliary cleanup does not lock later saving, export, backup, restore, deletion or browsing; never falsely report success or wrongly delete committed data.
- Judge performance by the complete usage path, avoiding repeated computation and full reads; formal data gets no arbitrary quota, and automatic history, temporary resources and caches are governed by budgets with a basis, protecting current and unfinished work. Performance trade-offs involving quality, permissions, cost and necessary checks must be explained.
- Verify by risk level: reuse valid evidence, and widen checks only because of new changes, failures or explicit risks; real failures take priority over green tests. Keep original words, explanation, authorization and acceptance apart, report code completion, automated verification, installation acceptance and release verification separately, and do not extend the scope of positive feedback.
- This repository keeps only the product source code, tests and public usage notes; run `npm run check:public` before committing, and do not commit personal data, local machine paths or credentials.
